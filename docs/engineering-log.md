这份文档记录开发过程中**实际测出来的问题**和**做过权衡的决定**。写给两类读者：接手代码的人，以及需要在面试里把这个项目讲清楚的作者本人。

每条坑都带实测数字。没有数字的条目不进这份文档——「我觉得这样更好」不算发现。

## 二、踩过的坑

### 坑 #1：思考模型让流式输出彻底失效，而瓶颈根本不在我以为的地方

**现象**：本机 Ollama 跑 `qwen3:8b`，每回合 15～25 秒，全程一片空白。我判断问题在输出格式——一次性输出完整 JSON，半个 JSON 没法展示给玩家，所以那 20 秒必然是空白等待。于是把回合拆成两阶段（先 JSON 决策、后纯文本流式说话）。

**改完之后更慢了**：首字延迟 30 秒，总耗时 30.3 秒。首字延迟约等于总耗时，流式毫无效果。

**根因**（分解测量得出）：

```
首个 reasoning 块 0.69s | 首个可见块 39.57s | 总 39.7s
reasoning 长度 1304 字 | 可见长度 5 字   （可见内容：'没怎么注意'）
```

`qwen3:8b` 是思考模型。Ollama 把 `<think>` 走 `delta.reasoning_content` 单独流，`delta.content` 要等推理块写完才开始。端点 0.69 秒就有响应、流式通路完全正常——**它先写 1304 字推理，才说 5 个字台词**。两阶段拆分等于付两遍推理，所以更慢。

**修法**：`extra_body={"reasoning_effort": "none"}`。首字延迟 2.2 秒，总耗时 2.6 秒。

**为什么做成开关而不是硬编码**：严格端点（OpenAI 官方）会因为未知字段直接 400。所以走 `GENSOKYO_REASONING` 环境变量，只在显式配置时才发。

**排除过的无效方案**（都试过）：`extra_body={"think": false}` 被 `/v1` 忽略；`chat_template_kwargs.enable_thinking=false` 无效；prompt 尾部加 `/no_think` 无效。只有原生 `/api/chat` 的 `think:false` 有效，但那是另一个端点。

**教训**：**优化前先分解测量，不要凭架构直觉判断瓶颈。** 我对着输出格式做了一整轮重构，而真正的原因是一个模型配置项。两阶段拆分本身有独立价值（见亮点 #3），但它不是这个问题的解。

### 坑 #2：NPC 到了门槛也不给线索，因为复读会自我强化

**现象**：玩家给灵梦投了 4 次赛钱、好感 24（正好达到线索门槛），直接问她「现在可以说了吗」，她回「你管的太多了」。继续投到好感 30，问三次，三次都是同一句。玩家的直接反馈是「灵梦笨笨的」。

**第一步排查**：把决策阶段的 prompt 单独拉出来，确认引擎确实告诉了她「条件已满足，现在可以说出来。用 reveal_info，fact 参数填 barrier_anomaly_time」。然后连采 5 次决策：

```
干净历史: reveal_info 命中 3/5
```

她**会**调，只是不稳定。所以不是模型不懂，是有别的东西干扰。

**第二步**：复刻实际游戏里那段被她自己的敷衍话灌满的对话历史，同样条件再采样：

```
被敷衍话灌满的历史: reveal_info 命中 1/5
```

**根因确认**：她说过一次「你管的太多了」，这句话进入对话历史，模型看到这个模式就倾向于继续敷衍。**复读是自我强化的**，而且它同时压低了工具调用率——不只是台词单调的问题，是玩法直接卡死。

**修法**：不调 prompt 语气，而是**让引擎停止指望模型自己想明白**。门槛开没开、线索齐没齐，引擎本来就知道，把结论直接写进 prompt 的独立段落：

```
【现在该做的事】
来访者已经让你觉得值得开口了。他一旦问起，就用 reveal_info 把这件事
告诉他（fact 参数填 barrier_anomaly_time），别再打发他走。
```

同样的脏历史下，**命中 8/8**。

**教训**：**引擎已经知道的事，不要让小模型重新推导一遍。** 这是本项目最重要的一条方法论，也是它和「把状态塞进 prompt 让模型自己看着办」这类做法的根本区别。派生出的一般原则：

- 能规则化的判定，规则化（工具前置条件）
- 已经算出来的结论，直告（【现在该做的事】）
- 只把真正需要语言能力的部分留给模型（说什么话、用什么语气）

### 坑 #3：结局不可达，因为让模型自己规划两跳路径

**现象**：三条线索齐了，玩家说服魔理沙一起去无缘塚。她答应了——「要处理那些花的话，先给我点情报换路费吧，就是这样」——然后：

```
✗ 从雾雨魔法店没法直接过去。
```

雾雨魔法店到无缘塚要经人间之里两跳。她只调了一次 `move` 直奔目的地，失败后重试也没想到连走两步。玩家走到无缘塚，那儿没人，「这里没有人回应」。**结局根本触发不了**，而这是唯一的通关路径。

**根因**：和坑 #2 同类——让 8B 模型看着出口清单自己做路径规划。prompt 里甚至写了「从这里未必一步到位，可以连着走」，无效。

**修法**：新增 `travel_to` 工具，引擎做 BFS 最短路，逐跳 emit 事件（回放能重现完整路线）。灵梦和魔理沙在原作里都会飞，直接飞过去符合设定。

**顺带避开的陷阱**：`travel_to` 必须同时加进芙兰的 `deny_always`。否则她能绕过 `move` 飞出地下室——她「被禁足」这个人设约束会被一个新工具无声破坏。已加测试锁住。

**教训**：**每新增一个工具，都要重新检查所有既有的行为约束是否还成立。** 见坑 #4，这是同一个问题的两次出现。

### 坑 #4：工具默认全开，每加一个工具就自动授予所有角色

**现象**：审查时实测发现 `break_item`（破坏物品）对灵梦和魔理沙也可用：

```
reimu  mode=normal      break_item in available_tools = True  | apply ok=True
marisa mode=excited     break_item in available_tools = True  | apply ok=True
```

而设计意图是「只有芙兰进入 destructive 情绪模式时才解锁」。

**根因**：`available_tools` 是默认全开的黑名单模型：

```python
allowed = set(TOOL_REGISTRY) - set(card.tools.deny_always)
```

灵梦和魔理沙的 `deny_always` 都是 `[]`，所以什么都能用。芙兰之所以被挡住，靠的是 `calm` 模式里显式写了 `tools_deny: [break_item]`——**是 calm 的 deny 在把守，不是 destructive 的 allow 在解锁**，`tools_allow` 其实是冗余的。

**修法**：`ToolSpec` 增加 `restricted: bool`，受限工具不进基线，只能由当前情绪模式的 `tools_allow` 显式解锁。于是 YAML 里写的东西终于名副其实。

**教训**：**权限模型的默认方向决定了长期安全性。** 默认全开意味着每次扩展都是一次静默的权限扩散，而且这类 bug 不会让测试变红——它让「设计意图」和「实际行为」悄悄分叉。

### 坑 #5：pydantic 默认忽略未知字段，让数据驱动的承诺变成静默失败

**现象**（实测 pydantic 2.13.4）：角色卡 YAML 里把 `tools_allow` 拼成 `tools_alow`，**不报任何错**，字段带着默认值 `[]` 上线。

**为什么严重**：整个设计押在「角色差异全部由 YAML 承载，加第四个 NPC 只需新增一个文件」上。而所有**有默认值**的字段（`tools_allow`/`tools_deny`/`forbidden_phrases`/`is_clue`/`decay_per_tick`…）一旦拼错都会静默退回默认值。表现出来是「情绪 gate 不生效」「禁语没拦住」这类行为 bug，而不是加载失败——**最难查的那种**。

唯一会报错的情况是拼错的名字顶替掉了必填字段。

**修法**：`StrictModel` 基类（`extra="forbid"`），所有定义模型继承。加三个「拼错必须报错」的回归测试。

**教训**：**fail-loud 的成本在写代码时，fail-silent 的成本在查 bug 时。** 后者贵得多。

### 坑 #6：游戏做出来是不可通关的

**现象**：内容写完后做完整性检查，发现 `offering_coin`（赛钱）不在任何地点的 `items` 里，也不被任何 `traded_item_in` 引用——**玩家无处可得**。而灵梦的线索门槛是好感 40、送一次礼 +6，需要 7 次；芙兰的 60 需要 10 次；全世界可拾取物品只有 5 件。

**三条线索里两条锁死，游戏不可通关。**

**修法**：玩家初始带 8 枚赛钱；灵梦门槛 40 → 24（4 次），芙兰 60 → 12（2 次）。芙兰的门槛应该**最低**——她被关了 495 年，谁来看她都立刻是朋友，低门槛比高门槛更符合人设。

并加回归测试锁住可通关性：

```python
def test_four_gifts_exactly_unlock_reimus_clue() -> None:
    """门槛与 ATTITUDE_DELTA 的比例一旦改动，这个测试会立刻报警。"""
```

**教训**：**内容和数值也需要测试。** 「玩法参数」听起来像是可以随便调的软性东西，但它决定游戏能不能玩通，比大部分代码逻辑更该被锁住。

### 坑 #7：未知斜杠指令被当台词发给 NPC

**现象**：玩家输入 `/move 人间之里`（正确的是 `/go`），游戏把这整行字符串当对话喂给模型，灵梦一本正经地回应它。玩家的观感是「她像个傻子」。同类：`/give   赛钱`（多打空格）也被当成说话。

**根因**：CLI 用 `raw.startswith("/go ")` 这种逐条前缀匹配，没匹配上的就落到 `session.say(raw)`。

**修法**：统一解析（`partition(" ")` + 别名表），认不出就提示而不是喂给模型。别名表里 `/move` `/walk` 都映射到 `go`。顺带 `import readline`——不 import 的话方向键会输出 `^[[A`。

**教训**：**LLM 应用里，「兜底路径」的默认目的地必须是安全的。** 把无法识别的输入交给模型，等于让模型替你处理你没想到的情况——它会认真回应，而结果是荒谬的。

### 坑 #8：一处会让线索永久拿不回来的软锁

**现象**：加了「玩家在无缘塚待久了会遗忘线索」的机制后，玩家忘掉线索、回去再问同一个 NPC，她回一句「这件事你已经告诉过对方了」——**不重新给出线索**。

**根因**：我之前为了防止 `event_log` 被同质事件灌满，给重复揭示加了短路，判据是 `npc.revealed_facts`。玩家遗忘后 `known_facts` 掉了，但 `revealed_facts` 还在。

**修法**：短路条件改成「**玩家仍然知道** 且 她说过」。遗忘于是可恢复，还多了个不错的桥段：你忘了只好回去再问，而她觉得你莫名其妙。

**教训**：**两个独立机制各自正确，组合起来可能产生死锁。** 这类 bug 只能通过「把新机制和所有既有机制逐一对撞」发现，写新代码时不会想到。

### 坑 #9：遗忘机制若挂在时间上，读档会让丢掉的线索凭空回来

**现象**（设计阶段就预见并避开）：遗忘最自然的实现是挂在 `tick()` 上（每回合累积）。但 `replay` 刻意不重放 tick——tick 只影响情绪衰减，而衰减节奏属于会话层编排。

于是：玩家忘掉一条线索、存档、读档，那条线索会回来。**存档背叛了玩家的实际经历。**

**修法**：遗忘按「玩家在无缘塚采取的动作次数」累积，进动作日志，能被精确回放。并写测试锁住：

```python
def test_forgetting_survives_replay_exactly() -> None:
    """注意这里全程只用动作构造场景——直接给 known_facts 赋值不进动作日志，
    回放自然重现不出来。"""
```

**这个测试第一次写的时候还是错的**：我直接给 `known_facts` 赋值来构造场景，而那不是动作，回放当然重现不出来。测试自己的前提错了。

**教训**：**「什么进存档」这个决定会传染到所有后续机制。** 定下「存档只存动作日志」之后，任何新机制都必须问一句：它是动作的结果，还是时间的结果？

### 坑 #10：内部标识符泄漏进 prompt 和玩家屏幕，清了四轮

英文 id 紧贴中文出现在给模型看的文本里，模型有概率把它们说出口。四轮都是同一类问题的不同位置：

1. `gate_hint` 渲染成「对方需先给你其中一样东西：rare_book、magic_mushroom」——而 `_item_name()` 就在同一个类里
2. 情绪变量名 `annoyance`、模式名 `calm`、阶段枚举名 `S0_UNAWARE` 直接进 prompt，还紧贴中文没空格（「你的annoyance是」）
3. 物品清单 `rare_book×1`——**同一个 prompt 里 `gate_hint` 刻意转了中文，【这里的东西】却没转**，代码注释自己被代码违反了
4. 系统提示末尾「你不了解也不会谈论：modern_technology、outside_basement_events」

第 4 条最有意思：这批字符串同时承担**机器键**（`OUTSIDE_BLIND` 用它做信息隔离判定）和**给模型看的散文**两个角色。这正是 `ErrorCode` 与 `error` 分家要避免的错误，我在一个地方守住了、在另一个地方犯了。

**修法**：`KnowledgeCfg` 拆成 `blind_to_outside: bool`（机器开关）和 `forbidden_knowledge: list[str]`（中文散文）。

**为什么漏到第四轮**：守这件事的测试有两个盲点——只检查 `messages[-1]`（user 消息）从不检查 system；泄漏词表里列的全是当前数据里**已经不存在**的词（`annoyance` 早就改成中文了），所以它一直在空转。

**教训**：**一个从未见过红的测试等于没有测试。** 后来我给所有新加的关键测试都做了突变验证——故意破坏实现，确认它真的会红。

### 坑 #11：三个空转的测试

审查发现的，都是「看起来在测、实际永远不会失败」：

1. `assert turn.mode_after in {"calm", "destructive"}` —— 覆盖了芙兰全部可能取值。而且测试场景里没有任何会改变情绪的动作，`mode_after` 恒为 `"calm"`，它没有构造任何 transition
2. `test_replay_reproduces_state_and_event_log` 声称验证 state 复现，实际只断言了 event id 列表和 `quest.stage`。里面还留着一行 `replayed.state.player.inventory.setdefault(...)`——一个什么都没做的补丁，像是与某个分歧搏斗后的痕迹
3. 泄漏词表全是不存在的词（见坑 #10）

**顺带发现的覆盖漏洞**：全仓没有任何地方断言 `npc.mode == resolve_mode(card, npc.emotion)`。情绪状态机的核心不变量无人看守，`bump_emotion` 里漏掉 mode 重算也没有测试会红。

补测试时又踩了一次：加进属性测试后做突变验证，**它没有红**——因为随机动作池里根本没有能跨越情绪模式边界的路径（唯一的礼物是忘却之花，而灵梦收礼是情绪下降、会触底在同一模式内；魔理沙和芙兰在池子里到不了）。最后改成一个确定性测试走完整引擎路径，突变验证才见红：

```
assert marisa.mode == resolve_mode(card, marisa.emotion)
E  AssertionError: assert 'normal' == 'excited'
```

**教训**：**属性测试的价值取决于它的输入空间能不能到达关键状态。** 随机采样对「需要特定长序列才能触发」的条件几乎无效，那种条件要写确定性测试。

### 坑 #12：测试替身存的是活引用，让关键断言空洞通过

**现象**（实测）：`ScriptedLlmClient.calls` 存的是调用方传入的 list 引用，不是快照。

```
before mutation len(calls[0]) = 1
after  mutation len(calls[0]) = 2
calls[0] is msgs = True
```

**为什么严重**：策略层最自然的写法是复用同一个 messages 列表就地追加。那样所有 `calls[i]` 都指向同一个对象、内容相同，于是「第二次调用的 prompt 里含回灌的错误原因」这条断言会**空洞通过**——第一次调用也「含」它。而这正是失败自愈机制的核心断言。

**修法**：`self.calls.append(list(messages))`。

**教训**：**测试替身的保真度决定了它能验证什么。** 一个存活引用的 spy，看起来在记录历史，实际只记录了最终状态。

---

### 坑 #13：贪婪正则提取 JSON，被中文模型的装饰花括号打败

**现象**：用 `re.compile(r"\{.*\}", re.DOTALL)` 抓 JSON，实测这些输入全部解析失败：

| 输入 | 结果 |
|---|---|
| `{"thought":"t","utterance":"u"} 顺便说下{笑}` | RAISE `Extra data` |
| `注意{重要}：{"thought":"t","utterance":"u"}` | RAISE `Expecting property name` |
| `{"utterance":"a"} {"utterance":"b"}`（模型输出两个对象） | RAISE `Extra data` |

贪婪匹配从第一个 `{` 吞到最后一个 `}`。中文模型带 `{笑}`、`（{重要}）` 这类装饰标记的频率不低，有些小模型还会先输出草稿再输出终稿。

**为什么值得修**：解析失败在策略层要付一次重试——玩家的等待时间直接翻倍，而这个解析器在每个 NPC 回合的热路径上。

**修法**：花括号配平扫描，逐个产出候选，取第一个能解析成 dict 的。字符串字面量内的括号不计数。

**教训**：**LLM 输出的噪声形态是可枚举的，值得专门测。** 我列了 10 种真实噪声形态逐个实测，比「加个 try/except 兜住」有效得多。

---

### 坑 #14：说话和工具调用产生两条不同的台词

**现象**（3 个真实回合里 2 个出现）：决策阶段调 `say("结界？最近倒是没看到什么异常。不过赛钱箱空着可真烦人。")`，而玩家屏幕上流出去的是「收钱的事倒是挺重要的。」`event_log` 里于是有两条 `npc_utterance`，**其中一条玩家从没看见**——而 event_log 是「唯一真相来源」。

**根因**：说话已经拆成第二阶段了，但 `say` 还留在决策阶段的可用工具列表里。

**修法**：`say` 从决策阶段的工具列表里摘掉，并且模型幻觉出来也丢弃（两层）。

**教训**：**重构出一个新阶段之后，要检查旧阶段有没有残留同一职责的入口。**

## 三、刻意的设计取舍（不是坑）

### 取舍 #1：`world/` 零依赖，一切状态变更走单一入口

`src/gensokyo/world/` 不 import 项目内任何其他模块，不含 LLM 调用，不做网络 IO。`WorldEngine.apply()` 是唯一的状态变更入口。

**换来的**：整个世界逻辑（工具前置条件、任务状态机、态度与情绪计算）在 1 秒内跑完全部单测，零成本、零网络。这是能反复调平衡的前提——如果每次验证都要跑 LLM，迭代速度会掉一个量级。

**验证方式**：审查时按**写操作**而非 import 查了一遍——`world/` 之外对 `state.*` 的赋值/`.add()`/`.append()`/`del` 零命中。`apply()` 之外确实没有第二条改状态的路。

### 取舍 #2：存档存动作日志，不存事件日志

事件 payload 里 `move` 的 `to` 是地点、`give_item` 的 `to` 是目标 NPC，同名不同义，从事件反推动作会猜错。所以存动作日志，事件是它的推导产物——只有一份真相，不会不一致。

**代价**（明确的契约边界）：`replay` 不重放 tick，所以重建后的情绪值会与存档那一刻不同，`mode` 原则上也会分叉，随之 `available_tools` 也会。实测确认：

```
npc          原情绪    重建情绪    原attitude  重建attitude
marisa      0.0300    0.4500          6            6
```

`attitude` / `inventory` / `known_facts` / `quest.stage` 完全一致，差异只在情绪。**回放保证动作因果，不保证时间流逝的产物。**

### 取舍 #3：回合拆成决策与说话两阶段

虽然它没解决延迟问题（见坑 #1），但保留了，因为有独立价值：**拆开之前 NPC 是盲着说话的**——工具调用成没成功她并不知道就把话说了。现在她能看到实际结果再开口。

代价是每回合固定两次调用。

### 取舍 #4：`ErrorCode` 与 `error` 分成两个字段

`error` 是给 LLM 看的自然语言（会回灌进下一轮 prompt，措辞反复调整），`error_code` 是机器可读枚举（供指标统计）。合成一个字段的话，改一句提示文案就会让历史指标断档。

### 取舍 #5：情绪增量按角色配置，不用全局表

同一事件对不同角色的情绪方向可能相反。灵梦的情绪变量是「烦躁度」而她爱钱，收到赛钱本该消气；芙兰收到东西该更兴奋。

原先用全局表的后果是：玩家送 4 次礼把好感刷到门槛的同时，把灵梦的烦躁度推到 0.82 进入 `irritated`、`ask_player` 被禁——**恰在给玩家奖励的那一刻让对话变差**。

### 取舍 #6：Persona 只做到「不出戏」，不追求指标极值

对「好玩」贡献最大的是 NPC 记住你、世界真的变化、情绪当场变脸。Persona 一致性从 0.82 提到 0.87 玩家基本感知不到。所以禁语清单 + 系统提示做到及格线即止。

## 四、还没做的（诚实清单）

按对 JD 的重要性排序：

1. **长期记忆**（JD 职责 4 整条）。目前只有 12 轮滑动窗口。分层记忆、情绪加权巩固、角色化遗忘率、沉睡记忆的强线索召回——schema 已经预留在角色卡里（`memory.lambda_decay`、`salience_multipliers`、`dormant_memories`），代码未实现。
2. **评测体系**（JD 职责 5）。有 190 个工程测试，但没有角色一致性、叙事合理性这类软指标的评测管线。助手腔污染率、行为分布偏离度这两个可硬化的指标最该先做。
3. **Reflection**。角色卡里有 `reflection_threshold`，未实现。
4. **对齐训练**（JD 职责 3）。用真实玩家轨迹做 DPO。这一条对可玩性贡献低，但它是 JD 明确要求、也是简历上唯一只能写「了解」的部分。
5. **Multi-Agent**。三个 NPC 目前各在一地、不会同场。同场时已知有两个缺口：送礼总给字母序第一个（`_npcs_here()[0]`）；NPC 之间的记忆不互通（世界层能通过近期事件串起来，记忆层不能）。

已知但未修的技术债：八处 `assert isinstance(args, XArgs)` 样板（`ToolHandler` 签名逼出来的类型收窄）、`_current_mode` 逻辑在三处重复、`session/save.py` 曾长期未接线（现已接）。
